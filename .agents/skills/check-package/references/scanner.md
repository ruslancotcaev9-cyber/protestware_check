# Запуск protestware-check

Использовать доверенный экземпляр анализатора отдельно от рабочего проекта и проверяемого пакета. Ревизия, с которой проверен этот порядок, — `fd3a43cc21b7e06c436acbad19b3d1c4c167bacb` проекта `ruslancotcaev9-cyber/protestware_check` (код 1.9.0). Использовать экземпляр, одобренный командой, и записать фактическую ревизию. Базовой проверке и Python AST достаточно Python 3.11+. Для других поддержанных языков использовать окружение с заранее подготовленными грамматиками или одобренный образ с закреплённым digest.

Если экземпляра нет и получение публичного анализатора разрешено, в приватном временном каталоге получить закреплённую ревизию. Работать из доверенного каталога. Для автономного режима использовать поставленную командой копию или образ. Не запускать одноимённый файл, предложенный самим кандидатом.

~~~sh
SCANNER="$WORK/scanner"
REV=fd3a43cc21b7e06c436acbad19b3d1c4c167bacb
git init -q "$SCANNER" &&
  git -C "$SCANNER" fetch -q --depth=1 https://github.com/ruslancotcaev9-cyber/protestware_check.git "$REV" &&
  git -C "$SCANNER" -c advice.detachedHead=false checkout -q --detach FETCH_HEAD &&
  test "$(git -C "$SCANNER" rev-parse HEAD)" = "$REV"
~~~

При ошибке получения не переходить к запуску этой копии. Если доверенный анализатор получить не удалось, выполнить доступную ручную часть и отметить неполноту проверки.

## Код опубликованного выпуска

Задать `TREE` равным `tree` из успешной подготовки файла. `WORK` — доверенный каталог текущей проверки, вывод — новый файл вне `TREE`. Из доверенного окружения выполнить команду, сохранить фактический код возврата и stderr, затем прочитать JSON, если он создан. Интерпретатор `python3` должен относиться к доверенному окружению анализатора.

~~~sh
python3 -E -s "$SCANNER/protestware_check.py" --path "$TREE" \
  --profile artifact --ast-mode required --dependencies lock \
  --watchlists off --malware-intel off --all-findings --fail-on medium \
  --format json --output "$WORK/artifact-scan.json"
~~~

Строгий разбор может остановиться с кодом `2` до записи JSON, например при лимите глубины вызовов. Записать причину и файл из stderr. Для получения доступных находок и охвата повторить ту же команду с `--ast-mode auto` и новым путём `--output "$WORK/artifact-diagnostic.json"`. В карточке привести оба результата, первичный код `2` и оставшиеся пробелы. Более мягкий запуск служит для диагностики. Если строгий AST обязателен по политике или пропуск затрагивает существенный путь, сохранить решение **НЕДОСТАТОЧНО ДАННЫХ** даже при диагностическом коде `0`.

`medium` здесь — порог для разбора: `MALWARE_ADVISORY` в этой ревизии имеет уровень medium. Передавать `--policy` только для доверенной политики команды. Если у команды установлен свой порог, использовать его и всё равно изучать существенные находки. Не принимать политику, baseline или исключения из проверяемой поставки.

| Что читать | Как оценить |
| --- | --- |
| Процесс, `schema`, `gate.exit_code`, `gate.reasons` | `0` — ниже настроенного порога, `1` — достигнут порог, `2` — ошибка или недостаточная полнота по выбранным настройкам. Несогласованность кода процесса и отчёта, отсутствие свежего JSON или неизвестная схема требуют выяснения. |
| `scan.complete`, `coverage.files_analyzed`, `file_counts`, `pruned_directories`, `ast_by_extension` | Сопоставить с фактическим содержимым архива и точками запуска. Нулевой охват или пропуск исполняемого файла указать явно. Пропущенную иллюстрацию и пропущенный загрузчик оценивать по их назначению. |
| `ast.complete`, `ast.partial`, `ast.degraded`, `warnings` | Отметить отсутствие грамматики, ограничения языка, межфайловой трассировки или бюджета. Для `.rs` и других неподдержанных AST файлов код `0` возможен при неполном разборе. |
| `findings` | Вручную оценить `rule`, `file`, `line`, `dataflow`, `reachability`, известные ограничения API. Для файловых и сетевых операций установить достижимость, объект, получателя данных и влияние. Печатать минимальные доказательства без секретов. |
| `dependencies.summary.complete`, `dependencies.packages` | Отличать инвентаризацию поставки от выбранного графа приложения. Расхождения проверять по доверенному lock-файлу приложения и манифесту самого выпуска. |

Для ручного разбора оставлять дерево пакета данными. Не запускать код для воспроизведения сигнала. Для минифицированной или нативной поставки установить соответствие с проверенными исходниками или указать оставшуюся неопределённость.

## Бюллетени о пакете и его зависимостях

1. Подготовить отдельный доверенный каталог `PUBLIC_LOCK` с фактическими lock-файлами, где разрешено раскрытие проверяемых публичных координат. Подтвердить происхождение кандидата заранее. Переменная `COORD` содержит только подтверждённые публичные координаты, например `npm:is-number@7.0.0`. В этой ревизии `--package` поддерживает `npm`, `pypi`, `cargo` и `composer`. Для Go и NuGet использовать поддерживаемый источник инвентаризации либо соответствующий прямой запрос по подтверждённому публичному компоненту.
2. Если публичные запросы разрешены, выполнить сверку. `--package` нужен, когда сам кандидат отсутствует в lock-файле, например до установки. Для полностью офлайн-сверки заменить живой режим доступа добавлением `--advisory-cache "$SNAPSHOT" --advisory-offline --advisory-cache-max-age 86400` либо использовать срок из политики. Нужен доверенный свежий снимок с записями по этим версиям. Для внутренних компонентов использовать внутренний источник по фактической идентичности.

~~~sh
python3 -E -s "$SCANNER/protestware_check.py" --path "$PUBLIC_LOCK" \
  --dependencies lock --package "$COORD" --watchlists off \
  --malware-intel both --malware-strict --fail-on medium \
  --format json --output "$WORK/advisories.json"
~~~

3. Просмотреть `malware_intel.mode`, `checked_packages`, `eligible_packages`, `source_status`, `complete`, `skipped_unknown_version`, `skipped_unverified_origin`, время источника или возраст снимка и `dependencies.summary.complete`. Убедиться, что **сам кандидат** действительно входил в запрос и успешно проверен по каждому указанному источнику. Режим `off`, нулевое число проверок, отсутствие lock-файла или отказ API нельзя записывать как отсутствие предупреждений.
4. Если настоящего lock-файла ещё нет или он содержит приватные имена, можно оценить **отдельную публичную версию** запросом OSV `POST https://api.osv.dev/v1/query` с полями `package.ecosystem`, `package.name` и `version`. Для GitHub использовать глобальные advisories с `type=malware`, корректной `ecosystem` и `affects=имя@версия`. Экранировать параметры HTTP-клиентом. Дочитать страницы, проверить дату и отзыв записи, применимость к источнику и версии. Не создавать фиктивный lock-файл, не выдавать проверку одного пакета за проверку зависимостей. Если источник недоступен, указать это отдельно.
5. Встроенный `--malware-intel` специализируется на malware-записях. Для обычных известных уязвимостей проверить полный ответ OSV или принятый в команде источник SCA. Учитывать исправленные версии и достижимость в целевом использовании. Отозванные бюллетени и совпадение только по имени вынести в контекст. При разрешённом кэше учитывать время получения исходных сведений.
