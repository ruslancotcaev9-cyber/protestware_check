## Основные группы правил

| Семейство | Примеры | Важная оговорка |
| --- | --- | --- |
| Контекст | `POLITICAL_RU`, `BLACK_MARK_OWNER`, `TOXIC_REPO`, `TOXIC_PACKAGE` | Репутационные/политические сигналы не подтверждают вредоносность |
| Advisories | `MALWARE_ADVISORY` | Сведения о точной версии, приоритет `medium`; не доказательство вредоносности и не общий CVE-сканер |
| Связанные действия | `SENSITIVE_DATA_SEND`, `AST_GEO_ACTION` | Передача потенциально чувствительных данных / удаление в географической ветви; требуется проверка назначения и достижимости |
| География | `GEO_DISCOVERY`, `GEO_TARGET`, `GEO_ACTION`, `CPP_GEO_ACTION` | Возможный control flow не доказывает выполненную операцию |
| Сеть | `NET_EXTERNAL`, `NET_DYNAMIC`, `NET_GEO_API`, `TAINT_URL` | Неизвестный хост или динамический URL часто легитимны |
| Файлы/процессы | `FS_DELETE`, `FS_WRITE`, `CPP_FS_DELETE`, `CPP_PROCESS` | Назначение API и конкретные пути требуют ручной проверки |
| Обфускация и DoS | `OBF_DECODE_EXEC`, `OBFUSCATED_JS`, `NETWORK_FLOOD` | Несколько сигналов повышают приоритет, но не доказывают атаку |

Категории риска в JSON — `none`, `low`, `medium`, `high` и отдельно информационные находки. `risk` включает находки внешних списков и malware advisories согласно правилам, а `code_risk` описывает только исходный код. `policy.risk` учитывает решения политики и baseline; порог применяется к нему, итоговый код находится в `gate.exit_code`. Конфигурация анализа влияет на итоговые числа.

## Полнота и ограничения

- Разбор производится **без исполнения проверяемого кода**, без сборки проектов и запуска install hooks.
- GitHub API может вернуть неполное дерево или лимит; повреждённый/обрезанный источник не должен интерпретироваться как успешно проверенный. Учитывайте `--max-bytes`, `--max-files`, `--max-total-bytes` и исключённые файлы. Неполное чтение приводит к коду 2; строгие проверки AST, зависимостей и advisories управляются отдельными параметрами.
- По умолчанию некоторые vendored/minified/binary файлы исключаются; такой объект может потребовать отдельной проверки. Существуют ограничения на количество обрабатываемых узлов и глубину вызовов.
- Python и Go/C#/JS/TS реализуют ограниченный межфункциональный taint-анализ **одного файла**. C/C++ имеет ограниченный граф вызовов в одном файле с глубиной до 6; не разрешает межфайловые символы, виртуальные вызовы, сложные перегрузки, макросы и полноценную типизацию.
- Tree-sitter AST не означает CFG/SSA или доказательство исполнимости конкретного ветвления. Трассировка `dataflow`/`reachability` требует ручной верификации и учёта реальных entry points.
- `--ast-mode required` контролирует разбор только языков с поддерживаемым AST-парсером. Он не требует AST для остальных расширений или наличия хотя бы одного AST; каталог только с `.rs`, документацией или без файлов может вернуть код 0 при `ast.complete=false`.
- Для SQL/HTML/CSS/SCSS/Less анализ преимущественно синтаксический/эвристический; `.sass` разбирается частично без полной грамматики.
- Внешние списки отражают непроверенные утверждения третьих лиц, часто по владельцу или историческому коммиту. Они не входят в SBOM как подтверждённые `vulnerabilities`.
- В `--dependencies registry` официальный реестр даёт метаданные, но не полное воспроизводимое разрешение диапазонов версий. Для точного графа нужны поддерживаемые lock-файлы; `--dependency-strict` помогает явно сигнализировать о неполноте.

## Реализация безопасности

Внешние URL из анализируемого кода не вызываются сканером. Запросы делаются лишь при выбранных `--repo`, `--watchlists live`, `--dependencies registry` или `--malware-intel osv|github|both` к предусмотренным источникам данных. После подготовки окружения AST использует только локально закэшированные грамматики. При необходимости строгой сегментации используйте локальные входные данные и предварительно сохранённые списки, отключив внешнюю сеть после установки пакетов и грамматик.

О проблемах безопасности **самого сканера** сообщайте по [SECURITY.md](../SECURITY.md). Данные о безопасности сторонних проектов передаются соответствующим upstream-maintainers.


Ограничения сетевых ответов: GitHub repository API — 16 000 000 байт;
официальные реестры — 1 500 000; каждый внешний список — 6 000 000;
advisory API — 2 000 000. Перенаправления отключены. Для repository API
нет отдельного общего лимита числа запросов: на каждый выбранный blob нужен
отдельный запрос; лимиты источника и квота GitHub остаются существенными.
Суммарный бюджет текста проверяется при приёме очередного файла в анализ.

`scan.complete`, `ast.complete`, полнота инвентаризации и полнота advisories
имеют разные значения: [таблица интерпретации](USER_GUIDE.md#5-интерпретация-отчётов-и-ci).
Остановка по лимитам межфункциональных вызовов, рекурсии, выражений и поиску
сетевых путей даёт диагностику частичного анализа. В `auto` сохраняются доступные
находки и `ast.complete=false`, в `required` — код 2. Превышение общего бюджета
узлов или глубины Python-интерпретатора может прекратить проход с управляемой
ошибкой. Это не заменяет ограничения CPU/памяти процесса для недоверенных данных.

### Особенности Go

`go.mod` задаёт объявленные требования и признаки `indirect`; `replace` меняет
фактическую идентичность источника, причём замена конкретной версии имеет
приоритет перед общей. Без экспорта локальные замены не разрешаются; при доверенном
импорте их файлы внутри source-root читаются для проверки хешей, код не выполняется.
`go.sum` дополняет требования контрольными суммами; запись `/go.mod` не означает
наличие контрольной суммы архива. Формат `h1` проверяется синтаксически, сами
артефакты не загружаются и их контрольные суммы не проверяются.

Другие версии из `go.sum` не добавляются к требованиям: их число отражено в
`dependencies.summary.go_unselected_checksums`. Без `go.mod` записи сохраняются
как `source=checksum`, `go.sum-only`, с неизвестным составом сборки. Требования
сохраняются даже при отсутствии соответствующей контрольной суммы.

Сканер не выполняет Go MVS и не читает граф всех транзитивных `go.mod`; без импорта модуль
с требованиями имеет `go-build-list-unverified` и `summary.complete=false`,
а `--dependency-strict` возвращает 2. [Доверенный импорт](BASELINE_AND_GO_IMPORT.md)
добавляет выбранное замыкание производственных пакетов для явно указанных профилей.
Полнота такого импорта относится только к этим целям и профилям.
Основание: [официальное описание go.sum](https://go.dev/ref/mod#go-sum-files).

[Отчёт проверки от 09.11.2026](SECURITY_REVIEW_2026-11-09.md) фиксирует
проверенные версии, сценарии и границы вывода; это снимок состояния, а не
постоянное утверждение о безопасности последующих коммитов.

## Политика и контекст

Политика не удаляет исходные наблюдения: исходный риск и решение gate хранятся
отдельно. Покрытие, baseline, метрики и GitLab описаны в [отдельном руководстве](POLICY_AND_CI.md).
Пагинация и снимки — в [методологии advisory](MALWARE_INTELLIGENCE.md#снимок-пагинация-и-лимиты-v120).

Baseline schema 2 сравнивает весь выбранный набор недокументационных входов,
а не только evidence находки. Для успешно разобранного Python используется AST
без координат, для остальных входов — текст; `.md`, `.mdx`, `.rst` исключены
только из контекстного хеша и по-прежнему сканируются. Изменение другого файла
проекта может консервативно вернуть все известные находки на ревью.
Это не добавляет межфайловый анализ достижимости.
[Формат контекста и миграция](BASELINE_AND_GO_IMPORT.md).

## Дополнительные поведенческие правила

`SENSITIVE_DATA_SEND` поддерживает встроенный Python AST: ключи окружения с
признаками TOKEN/SECRET/PASSWORD/API_KEY и др., непосредственные чтения известных
имён файлов учётных данных, передачи в URL/params/headers/cookies/data/json/auth/files.
Есть внут­рифайловое связывание параметров/возвратов. Статический внешний HTTP-host
вне allowlist даёт high, неизвестный — medium; confidence остаётся medium.
Сам секрет/файл не читается сканером. Разрешённый домен снимает именно этот сигнал,
а не остальные правила. Список имён источников ограничен; произвольные способы
чтения, Session-клиенты, межфайловые обёртки и фактическая авторизация не доказываются.

Для Go/C#/JS/TS `AST_GEO_ACTION` связывает известные операции удаления с RU/BY-
условием в синтаксической ветви. Это ограниченная внут­рифайловая корреляция;
полного связывания типов, межпроцедурного CFG и runtime-entry-points нет.
Литеральные Boolean-условия и короткое замыкание частично учитываются, но произвольная
достижимость не вычисляется. `confidence` не является калиброванной вероятностью.

Для Go `GO_FS_DELETE` при успешном AST-разборе разрешает вызовы `os.Remove` и
`os.RemoveAll` через обычный импорт, алиас или dot import. Учитываются параметры,
receiver, локальные объявления, блоки, циклы, if и type switch. Строки, комментарии,
другие пакеты и затенённые имена не превращаются в вызов `os`. Результат содержит
`resolved_symbol`; `AST_GEO_ACTION` использует те же разрешённые вызовы.
Алиасы значений функций (`rm := os.Remove; rm(path)`), объявления из других файлов
и полная проверка типов не разрешаются. Смешанные неоднозначные dot import дают
диагностику неполноты. При недоступном AST или `off` остаются ограниченные
текстовые эвристики без этой гарантии разрешения имён.

### Node.js и TypeScript

При полном успешном AST `FS_DELETE` для `.js/.jsx/.mjs/.cjs/.ts/.tsx` разрешает
`rm`, `unlink`, `rmdir` и их `Sync`-формы из `fs` / `node:fs`, а также promise API
из `fs.promises` или `fs/promises` / `node:fs/promises`. Поддержаны ESM namespace,
default/named import, литеральный CommonJS `require`, деструктуризация, локальные
псевдонимы, статические имена свойств, optional calls и основные TS-обёртки
выражений. Unicode-экранированные имена нормализуются без `eval`.

Параметры, локальные объявления, блоки, catch/циклы, var-hoisting и runtime enum
могут затенять импорт. Type-only import не становится runtime API. Прямое
переприсваивание имён и записей в известные свойства учитывается ограниченно.
В JSON/SARIF сохраняются `resolved_symbol` и `binding_certainty` (`resolved` либо
`possible`, если есть неизвестная альтернатива). Это определённость связи с API,
а не оценка вредоносности или доказательство достижимости.
`AST_GEO_ACTION` использует те же файловые вызовы; прежняя эвристика Deno сохранена.

Для импортированных `child_process.exec/execSync` сохранён файловый сигнал,
если статический префикс команды соответствует поддержанным `rm -…` или `del /…`.
Это узкий разбор префикса, не интерпретатор shell и не поддержка всех process API.
API описаны в официальной документации [Node fs](https://nodejs.org/api/fs.html#promises-api)
и [child_process](https://nodejs.org/api/child_process.html#child_processexecsynccommand-options).

Ограничения: один файл, без полной проверки типов/CFG, межфайловых переэкспортов,
`createRequire`, динамических модулей и TS `import =`. Тела функций рассматриваются
при обходе; CommonJS-инициализация, расположенная позже тела функции, может быть
неизвестна. Изменения через другие вызовы, отражение и динамические свойства
учитываются неполно. Слияние изменений namespace после ветвления консервативно
и может потерять возможный нативный путь. Успешный AST не означает полного
семантического покрытия JavaScript.

Бюджеты: 120 000 посещений, глубина обхода 250, глубина значения 30. Их исчерпание,
а также неразрешённая вычисляемая запись в известный native namespace дают
диагностику неполноты. В `auto` частичный анализ сохраняет прежние эвристики;
при полном JS/TS AST текстовый `FS_DELETE` заменяется результатами разрешения.
В `off` и без AST гарантия импортной идентичности отсутствует. `required` при
диагностированной неполноте возвращает 2. Изменение `js_bindings.py` входит в
контекст правил baseline schema 2 и возвращает известные находки на ревью.

### SQL

SQL-лексер скрывает строки, E-строки, dollar quoting, кавычечные идентификаторы и
вложенные блочные комментарии, сохраняя позиции. `SQL_DESTRUCTIVE` распознаёт
TRUNCATE в начале команды, с необязательными TABLE/ONLY и квалифицированными именами.
Текст в SELECT, литерале или комментарии не становится TRUNCATE-командой.
Для полного распознаваемого синтаксиса TRUNCATE проверяются опции ONLY, `*`,
RESTART/CONTINUE IDENTITY, CASCADE/RESTRICT; их ASCII-токены маскируются перед
общей Tree-sitter SQL-грамматикой с сохранением UTF-8-смещений. Неизвестный хвост
команды не скрывается. Исходные evidence и номера строк сохраняются.
Процедурные тела в строках и динамический SQL не раскрываются; `EXECUTE IMMEDIATE`
остаётся отдельным сигналом. Это не полная грамматика всех SQL-диалектов.

Основание: [области Go](https://go.dev/ref/spec#Declarations_and_scope) и
[синтаксис PostgreSQL TRUNCATE](https://www.postgresql.org/docs/current/sql-truncate.html).

## Известные пропуски и оценка

Прежние пропуски Go dot import, TRUNCATE без TABLE и `fs.promises.rm` исправлены
и входят в строгую регрессию. Расширенная оценка v4 содержит 72 примера,
58 целых файлов, 64 группы исходников и 15 проектов. По предложенным меткам:
TP=30, TN=36, FP=0, FN=6; 8 partial-анализов. Пропущены удаления через graceful-fs,
локальный removeSync, переэкспорты и обёртки rimraf. Два найденных fs-extra случая
с partial опираются на текстовый fallback, не на подтверждённый импорт.
Сохраняются ограничения динамического кода, межфайловых связей, типов и CFG.
Метки относятся к операциям, а не к вредоносности; независимого человеческого
подтверждения меток не проводилось.
