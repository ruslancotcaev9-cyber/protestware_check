## Выборка и метки

План: 24 новых целых файла из шести ранее не использованных репозиториев,
по четыре файла на язык: Go, C#, SQL, JavaScript, TypeScript, Python.
Для каждого языка вручную выбираются два положительных и два отрицательных
примера для правила удаления файлов/деструктивного SQL. Это целевая сбалансированная
выборка, не случайная и не оценка распространённости угроз. Выбор по назначению
файла и ручному изучению кода не является слепым независимым экспериментом.

Критерии входа: полный исходный файл с подходящей лицензией, до 100 000 символов
и 1 000 строк, без генерации/внешних project helpers, с зафиксированными
upstream path, Git blob SHA, UTF-8 SHA-256 и лицензией. Исходный путь/импорты
не переписываются. CRLF нормализуется только для code по действующему harness;
оригинальный fragment и Git blob hash сохраняются. Выбор файлов/обоснования
и журнал pending фиксируются отдельным коммитом до первого запуска детектора.
Если на этапе чтения источников план невыполним, изменение плана фиксируется
до измерения; после получения результатов файлы не заменяются ради метрик.

Метка положительная при наличии в полном файле исполняемого синтаксического
вызова удаления/деструктивной SQL-команды, включая явно установленную обёртку.
Это не означает обязательное достижение вызова, malware или protestware.
Одноимённые методы других объектов, строковые примеры и комментарии сами по себе
не положительный evidence. Отрицательная метка относится только к целевому правилу.
Все метки предлагает ассистент; независимое человеческое ревью не выполнено.

## Измерение

Все новые cases: ast_mode=auto, один и тот же зафиксированный детектор,
без выполнения target-кода, установки его зависимостей или запуска сборки.
Набор fresh-v7.json и отдельный checksum-bound review ledger не смешиваются
с 56 сохранёнными external.json и 38 использованными promoted.json.

CI публикует TP/FP/TN/FN, ошибки, partial, backend и предупреждения по каждому
случаю и языку. Report-only допускает FP/FN, но не скрывает ошибки оценки:
ошибка backend/чтения/валидации блокирует задание. Неполный анализ остаётся
неполным даже при правильном исходе. Исходные JSON и контрольные суммы
сохраняются; после просмотра результатов эти файлы считаются использованными
и для следующей независимой проверки требуется новая выборка.

## Пределы вывода

Даже отсутствие FP/FN не подтверждает безопасность пакетов или качество на
всех проектах. Четыре файла одного проекта коррелированы; помощник предлагает
и метки, и этот план. Для независимой оценки качества нужен отдельный специалист,
подтвердивший метки и методику вне автоматического журнала. Обнаруженные проблемы
документируются; исправления правил выполняются отдельной следующей итерацией,
с переносом использованных примеров в регрессию и сохранением первого результата.
