## Область проверки

`--profile source` сохраняет прежний отбор файлов. `--profile artifact` дополнительно
проверяет `dist`, `build`, `.next`, `node_modules` и `*.min.js`. Оба профиля сохраняют
исключение служебных каталогов VCS/окружений, карт исходников и неподдерживаемых
расширений. Указанный пользователем `--exclude` действует в обоих профилях.
Используются glob-шаблоны `fnmatch`, а не правила `.gitignore`.

```bash
python protestware_check.py --path ../package --profile artifact \
  --ast-mode required --format json --output ../artifact-report.json
```

JSON `coverage` содержит `file_counts` (проверенные, исключённые по шаблону,
неподдерживаемые, бинарные, ссылки, слишком большие и нечитаемые файлы),
`files_observed`, `files_selected`, `files_analyzed`, `pruned_directories`,
`ast_by_extension`, объём входного/проанализированного текста и ограниченный список
примеров пропусков. `--coverage-max-samples` задаёт размер этого списка (0–10000,
по умолчанию 100); счётчики остаются полными в пределах перечисленной области.

Локально исключённые поддеревья не обходятся. Число содержащихся в них файлов
неизвестно: это явно отражено в `pruned_subtree_file_counts_unknown`. Входные пары
файл/текст, переданные библиотечному API, имеют `enumeration=provided`: выводов о
других файлах проекта такой отчёт не делает. GitHub-вход при использовании CLI
разрешается в коммит до чтения дерева; сохраняются `resolved_commit` и `resolved_tree`.
Git-submodule отмечается отдельно и не скачивается.

`scan.complete` по-прежнему относится к чтению выбранных файлов. Исключения не
объявляются ошибками чтения; полноту области оценивают по `coverage`. Числовые
бюджеты файлов и байтов продолжают действовать в обоих профилях.

## Явная политика

```bash
python protestware_check.py --path ../application \
  --policy /trusted/policy.toml --format json --output ../report.json
```

Начальный файл: [examples/policy.toml](../examples/policy.toml). Политика загружается
только по `--policy`; файл из анализируемого проекта автоматически не применяется.
Формат — TOML, `schema=1`, неизвестные поля и неверные типы отклоняются.
Для CI храните политику и baseline в защищённой ветке или доверенной конфигурации,
чтобы анализируемое изменение не могло само разрешить свои находки.

| Раздел | Поля |
| --- | --- |
| `[scan]` | `profile`, `exclude`, `allow_domains` |
| `[gate]` | `fail_on`, `only_new`, `require_complete` |
| `[rules.RULE_ID]` | `severity`, `enabled`, `reason`, `owner`, `expires` |
| `[[suppressions]]` | Точные `rule` и `fingerprint`, `reason`, `owner`, `expires` |

Явные `--profile`, `--fail-on`, `--only-new`/`--all-findings` имеют приоритет над
соответствующими значениями политики. Списки CLI-доменов и исключений дополняют
списки политики. Переопределение серьёзности, отключение правила и подавление
находки требуют непустых обоснования и ответственного, даты `YYYY-MM-DD`.
Дата действует включительно по UTC. Просроченное исключение перестаёт действовать
и требует повторного рассмотрения, даже если находка есть в baseline.

Находки остаются в JSON/SARIF. Исходные `severity`, `risk` и `summary` сохраняются;
решение CI отражают `effective_severity`, `policy_decision`, `policy.risk` и
`gate.exit_code`. SARIF использует эффективный уровень и внешние `suppressions`,
сохраняя исходные сведения в `properties`. `confidence` обозначает уверенность
ограниченного статического анализа и не является вероятностью вредоносности.

`require_complete=true` требует отсутствия зарегистрированной неполноты включённых
этапов. При выключенном этапе он не включается автоматически. AST-контроль
применяется к поддерживаемым парсерам; неподдерживаемые языки видны в покрытии.
Без доверенного импорта Go модуль с требованиями останется неполным для строгой
инвентаризации. [Импорт выбранных профилей](BASELINE_AND_GO_IMPORT.md) принимает
готовые данные доверенного CI без вызовов Go внутри сканера.

## Утверждённый исходный отчёт

```bash
# Получить находки для рассмотрения и отдельный список их отпечатков.
python protestware_check.py --path ../application --format json \
  --output ../review.json --write-baseline ../baseline.json

# После рассмотрения baseline применять порог к новым и изменившим контекст находкам.
python protestware_check.py --path ../application --baseline ../baseline.json \
  --only-new --format json --output ../new-report.json
```

Экспорт baseline не утверждает находки автоматически: утверждение выполняется
процессом ревью. Формат содержит версию отпечатка, дату, версию инструмента и
SHA-256 отпечатки и контекст schema 2, без исходного кода. Отпечаток включает правило, исходный уровень,
путь, evidence и идентичность пакета/advisory, если они есть; номер строки не входит.
Он устойчив к сдвигам строк, но одинаковый фрагмент в одном файле может иметь
одинаковый отпечаток. Поэтому schema 2 дополнительно связывает весь выбранный код,
настройки, правила/парсеры, зависимости и политику. При изменении контекста прежние
находки становятся `updated` и возвращаются на ревью. Для Python используется AST
без координат; для остальных входов текст, исключая Markdown/RST. Это консервативная
проверка контекста проекта, без доказательства эквивалентности поведения.

`--only-new` требует явно переданный baseline. Старые находки остаются с
`baseline_state=unchanged`, если совпал контекст; новые — `new`, изменившие контекст —
`updated`. Schema 1 нельзя использовать для фильтрации: требуется рассмотрение и
новый экспорт schema 2. [Подробности и миграция](BASELINE_AND_GO_IMPORT.md).
Ошибки чтения и строгих этапов сохраняют
приоритет кода 2 независимо от baseline и подавлений. Отчёт, baseline, политику и
снимок нельзя записывать поверх друг друга. Для существующего файла внутри
проверяемого дерева действует запрет перезаписи.

## GitLab CI/CD

Используйте одинаковый `--project-id "$CI_PROJECT_PATH"` при создании baseline и
проверке, чтобы связать решения с конкретным проектом независимо от пути runner.

[Готовый пример](../examples/gitlab-ci.yml) рассчитан на Linux runner с Python 3.11+,
pip и git. В существующий pipeline нужно перенести задания и согласовать стадии.
Проверяемый проект не устанавливается и не собирается. Подготавливаются только
доверенные зависимости сканера и его грамматики; версия сканера закреплена SHA.
Для закрытого контура это окружение можно подготовить в утверждённом образе заранее.

1. `protestware_scan` запускает `scripts/gitlab_scan.py`, сохраняет свежие JSON,
   SARIF и `status.json`. При корректном отчёте задание возвращает 0 даже при
   находках или неполном анализе. Если отчёт не сформирован, задание завершается
   ошибкой; старый каталог результатов не используется повторно.
2. Обязательное `protestware_gate` проверяет наличие и SHA-256 JSON, согласованность
   статуса и `gate.exit_code`, затем возвращает исходный код 0/1/2. Отсутствующие,
   повреждённые и изменённые артефакты не дают успешного завершения.

Оба задания необходимы; для gate нельзя включать `allow_failure` или исключать его
из правил запуска. SHA-256 здесь обнаруживает несогласованность артефактов, но
не заменяет доверенную конфигурацию pipeline и управление доступом.
Скрипты интеграции ограничивают входной JSON 25 MB. Дополнительно действуют собственные
лимиты SARIF выбранной версии/инстанса GitLab; большой отчёт нужно рассматривать
также в JSON и разделять по обоснованным областям проверки.

В базовом примере отчёты доступны как артефакты во всех применимых редакциях.
Для GitLab Ultimate с поддержкой SARIF можно включить показанный в YAML блок
`artifacts:reports:sarif`: функция появилась в 18.11 за флагом и общедоступна с
19.2. GitLab принимает находки только от успешно завершившегося задания отчёта;
`allow_failure` у упавшего задания это не исправляет.
См. [официальную документацию](https://docs.gitlab.com/user/application_security/detect/sarif/).

Специальный экспорт GitLab различает advisory одного манифеста без номера строки
через отдельные стабильные `ruleId`, сохраняя исходный ID правила в `originalRuleId`.
Сигналы уровня репозитория без физического файла могут не отображаться в интерфейсе:
для полного рассмотрения сохраняется JSON.

## Корпус и измерения

```bash
python scripts/evaluate_corpus.py --measure --output ../corpus-metrics.json
```

[Корпус](../tests/corpus/cases.json) содержит 48 инертных строк исходного кода:
по 4 положительных и 4 отрицательных сценария для Go, C#, JavaScript, TypeScript,
SQL и Python. Проверяются конкретные правила: географически обусловленное
удаление, разрушительные SQL-операции, передача чувствительных данных. Метка относится
к ожидаемой находке правила, а не к установленной вредоносности целой программы.

Отчёт считает TP/FP/TN/FN, precision, recall и долю ложных срабатываний отдельно
по языку/правилу. Ошибка парсера делает метрики неполными и возвращает 2; FP/FN
возвращают 1. Подготовка всех грамматик обязательна для полного корпуса.
`--measure` добавляет время и пик памяти, видимой `tracemalloc`; память нативных
парсеров не измеряется. Это небольшой регрессионный корпус, а не оценка качества
на реальных проектах. GitHub CI сохраняет `corpus-metrics` как артефакт.

Дополнительно запускаются [два внешних набора](../tests/corpus/README.md):
`promoted.json` содержит 22 уже использованных примера и строго блокирует FP/FN;
`external.json` содержит 24 примера из других исходных файлов и публикует
реальные FP/FN в режиме `--report-only`. В 1.3.2 заменены все 8 использованных
JS/TS-примеров, 16 примеров других языков сохранены. Это не полностью новая
независимая выборка. Ошибки разбора остаются блокирующими.
CI сохраняет `corpus-metrics.json`, `promoted-corpus-metrics.json` и
`external-corpus-metrics.json` отдельно. В отчёт включены метаданные набора,
контрольный коммит детекторов, число групп исходных файлов и целых файлов.

Python AST теперь разбирается один раз для двух анализаторов. Межфайловое разрешение,
полный CFG, динамический код, макросы и фактическое выполнение остаются вне этой
итерации; выводы об ограничениях см. в [техническом справочнике](TECHNICAL_REFERENCE.md).

## Совместимость JSON-артефактов

Полный отчёт содержит `schema: 1`, status сохраняет schema 1. Gate проверяет
известную версию отчёта, первоначальный SHA-256, счётчики, риск и код завершения.
Старые отчёты 1.3.0-1.3.2 распознаются как ограниченный legacy-формат; неизвестные
версии и неоднозначный JSON блокируют gate. Основной helper gate не требует
jsonschema. Полная формальная проверка доступна через `scripts/validate_json.py`
после установки requirements-contracts.txt. [Контракты и миграция](JSON_CONTRACTS.md).
