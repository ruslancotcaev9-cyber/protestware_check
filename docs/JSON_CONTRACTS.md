# JSON-контракты и совместимость

Актуально для кода **1.5.0, unreleased**. [Указатель](README.md) ·
[Руководство](USER_GUIDE.md) · [Проверка версии](VALIDATION_1_4_0.md).

## Версии форматов

`version` в отчёте означает версию кода сканера, а `schema` — версию формата
данных. Начиная с 1.4.0 полный JSON-отчёт содержит `schema: 1`. Добавление этого
поля не меняет существующие поля, правила обнаружения или коды выхода сканера.
JSON-схемы описывают Draft 2020-12 и поставляются вместе с кодом:

| Данные | Схема | Назначение |
|---|---|---|
| Полный JSON-отчёт CLI | [report-v1](../schemas/report-v1.schema.json) | Результат после применения политики: находки, инвентаризация, покрытие, baseline и gate |
| Baseline schema 2 | [baseline-v2](../schemas/baseline-v2.schema.json) | Контекст рассмотрения и отпечатки версии 1 |
| Исторический baseline schema 1 | [baseline-v1](../schemas/baseline-v1.schema.json) | Только чтение/сравнение; фильтрация `--only-new` запрещена |
| Нормализованный Go-снимок | [go-build-info-v1](../schemas/go-build-info-v1.schema.json) | Данные экспортёра для производственного профиля; не сырой `go list` |
| GitLab `status.json` | [gitlab-status-v1](../schemas/gitlab-status-v1.schema.json) | Код сканера, наличие отчёта и SHA-256 его точных байтов |

Схема отчёта относится к `protestware_check.py --format json`. Внутренняя функция
`build_report` возвращает промежуточный результат без политики/gate; сначала
нужно вызвать `scan_policy.apply`. SARIF 2.1.0 и CycloneDX 1.6 используют свои
стандартные форматы. Схемы advisory-снимка и метрик корпуса в этот этап не входят.

## Проверка артефакта

Для полной формальной проверки нужны отдельные необязательные зависимости.
После их установки проверка работает без сети:

```bash
python -m pip install -r requirements-contracts.txt
python scripts/validate_json.py report ../reports/report.json
python scripts/validate_json.py baseline ../reports/baseline-v2.json
python scripts/validate_json.py go-build-info ../trusted-go/build-info.json
python scripts/validate_json.py gitlab-status ../reports/status.json
```

У helper два кода выхода: `0` — контракт прошёл, `2` — некорректные данные,
ошибка чтения, превышение бюджета или отсутствие зависимостей. Код `0` здесь
не означает отсутствие находок: отчёт с `gate.exit_code=1` может быть корректным.
Обязательный GitLab gate по-прежнему возвращает сохранённый код сканера 0/1/2.

Helper выбирает схему только из встроенного перечня. `$schema` и `$ref` внутри
проверяемого JSON не выбирают другую схему и не загружаются. Все ссылки внутри
поставляемых схем локальные; их `$id` — идентификаторы URN. Registry валидатора
не имеет сетевого загрузчика. При ошибке печатается вид контракта и нарушенное
правило, без значений и путей JSON-полей, которые могут содержать приватный код.

Основной сканер и GitLab gate сохраняют работу без `jsonschema`: они используют
предметные проверки стандартной библиотеки. Полная JSON Schema проверяется
этим helper и обязательными тестами CI. Она не включается скрыто при обычном
сканировании и не заменяет имеющиеся проверки доверия, лимитов и полноты.

## Структура и смысл

JSON Schema проверяет обязательные поля, типы, диапазоны, версии, отпечатки,
условные поля и известные перечисления. Дополнительные проверки устанавливают
отношения, которые не выражены структурной схемой:

| Контракт | Дополнительная проверка |
|---|---|
| Отчёт | Счётчики severity и решений политики соответствуют находкам; исходный/эффективный риск и код gate согласованы; неполное чтение не может пройти как код 0; число обработанных файлов согласовано с покрытием |
| Baseline | Точные типы версий, ограничения отпечатков и закрытый состав контекста; schema 1 не разрешает `--only-new` |
| Go | Канонические пути, точные версии, замыкание графа, отсутствие циклов, корневые пакеты и привязка манифестов |
| GitLab status | При отсутствии отчёта требуются код 2 и пустой digest; при наличии — SHA-256. Gate отдельно сопоставляет digest и код с самим отчётом |

Проверка Go helper не читает исходное дерево и не доказывает актуальность
хешей. При настоящем `--go-build-info` импортёр дополнительно проверяет ожидаемую
ревизию и текущие файлы. Аналогично, корректная структура baseline не означает
утверждения находок, а SHA-256 отчёта не удостоверяет личность производителя.
Конфигурация CI и источник артефактов должны быть доверенными.

## Безопасное чтение

Baseline, Go-снимок, окружение/листинги Go и артефакты GitLab отклоняют дубли
ключей, `NaN`, `Infinity` и переполнение до бесконечности. Для нормализованных
артефактов и окружения Go максимальная глубина дерева — 64, число узлов —
1 000 000. Сырой Go-листинг в виде JSON-массива проверяется с теми же бюджетами;
для последовательности отдельных объектов действуют предел 25 000 000 байт,
прежние лимиты количества объектов и валидаторы предметных полей.

| Файл, читаемый helper | Максимальный размер |
|---|---:|
| Отчёт | 25 000 000 байт |
| Baseline | 5 000 000 байт |
| Go build-info | 25 000 000 байт |
| GitLab status | 10 000 байт |

Принимаются обычные файлы; конечные символические ссылки и специальные файлы
отклоняются. Неверный JSON и чрезмерная вложенность дают управляемую ошибку.
Проверяемые фрагменты кода не импортируются и не исполняются.

## Миграция с 1.3.2

1. Потребители нового отчёта проверяют `schema == 1`, а версию сканера читают
   отдельно. Неизвестная версия схемы должна давать ошибку совместимости.
2. Для сохранённых отчётов **1.3.0–1.3.2**, у которых нет `schema`, helper требует
   явный режим совместимости:

   ```bash
   python scripts/validate_json.py report ../reports/legacy.json --allow-legacy-report
   ```

   Проверяется копия с интерпретацией схемы 1, исходный файл не переписывается.
   GitLab gate автоматически распознаёт только эти три известные старые версии;
   SHA-256 вычисляется по первоначальным байтам. Отчёт новой версии без `schema`
   или с неизвестной схемой не принимается, даже при совпадении digest.
3. Baseline остаётся schema 2, fingerprint — версии 1; Go/status остаются
   schema 1. Изменения кода валидаторов входят в контекст правил baseline:
   известные находки могут потребовать нового рассмотрения. Не обновляйте baseline
   автоматически ради прохождения gate.
4. Дубли JSON-полей и нечисловые значения теперь отклоняются; исправляйте
   производитель данных, а не удаляйте защитную проверку.

## Правила развития

В схемах разрешены добавочные поля там, где `additionalProperties` допускает
их. Читатель может игнорировать такую метаинформацию. Контекст baseline и профиль
Go имеют закрытый состав; новые поля в этих структурах требуют явного решения
о совместимости. Неизвестный номер `schema` не интерпретируется как текущий.

Удаление/переименование обязательного поля, несовместимая смена его типа,
добавление нового обязательного поля или несовместимое изменение перечисления
требуют новой версии формата и нового файла схемы. Добавочное необязательное
поле допустимо, если старые сохранённые артефакты продолжают проходить проверку.
Номер релиза сканера сам по себе номер схемы не меняет.

CI устанавливает закреплённые зависимости, проверяет схемы и текущие writer/reader,
а также [сохранённые фикстуры](../tests/contracts/README.md) 1.3.2. Проверяются
ошибки версий/типов, приватность сообщений, отсутствие сетевого разрешения схем,
отсутствие исполнения target-кода и коды 0/1/2. Исторические фикстуры нельзя
молча перегенерировать новым writer: это уничтожит проверку совместимости.

Структурная проверка и согласованные поля не доказывают безопасность проекта,
полноту всех путей исполнения или честность входного отчёта. Ограничения самого
анализа — в [техническом справочнике](TECHNICAL_REFERENCE.md).

[API jsonschema](https://python-jsonschema.readthedocs.io/en/stable/validate/),
